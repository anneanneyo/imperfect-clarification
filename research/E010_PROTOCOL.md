# E010: сопоставимость и результаты уточнений при одной конфигурации исполнителя

27 октября2026. Записано до загрузки новых final/judge-файлов. Baseline `belief` и его76 исходов известны из E008. Метаданные всех12 файлов уже проверены; факт их доступности не является результатом о качестве. Весь анализ development/exploratory, не закрытый тест нового метода.

## Источники и главный вопрос

Закреплённая ревизия BAG `58b2215ce80c74731d6d8dd3a843d2767943f569`; assistant Qwen3-8B, simulator Gemini2.5Flash, data_seed50, final_prompt=`prompt`, четыре reasoner variants: `belief`, `prompt`, `belief6`, `belief7`. Включить все четыре, шесть попарных сравнений, не выбирать по исходу.

Вопрос: какие наблюдённые ветви действительно сопоставимы по задаче, явной цели и зарегистрированной конфигурации финальной модели, и различается ли опубликованный итоговый verdict внутри них? Ни вопросная политика, ни отказ пользователя не рандомизированы; одно продолжение стохастично. Разность verdict не является истинной ожидаемой ценностью вопроса или общей причинной оценкой.

## Этап1: до просмотра новых исходов

Скачать12 файлов, проверить их Git blob/LFS hashes по ранее сохранённой инвентаризации и SHA256. Читать новые user-поля и final context/config/prompt, но не выводить/анализировать final generations и judge verdict. Файлы judge на этом этапе только хешируются, не разбираются. Если структура/поля не соответствуют ожиданию, записать причину, а не подменять её нулевой точностью.

Для каждого активного user-эпизода проверить:

- source ID уникален, исходный запрос/уточнение/ответ непустые;
- явная disambiguation содержит question и непустой список answer; reference равен одной группе с этими answer;
- final context в точности сохраняет question, clarification_q, user_answer, disambiguation и reference;
- prompt ровно `[user: исходный запрос, assistant: уточнение, user: ответ]`, direct_prompt=vanilla, без скрытой цели;
- processed_prompt содержит все три сообщения в порядке и совпадает с проверенным шаблоном после замены содержимого; сообщения не потеряны при зарегистрированной обработке;
- конфигурация final: model_name/assistant_model, final_prompt, direct_prompt, use_8bit, sampling и все resolved decoding/context parameters. batch_size учитывать отдельно: совпадение основных параметров не доказывает идентичность численных условий inference, фактической ревизии весов/API snapshot или RNG.

Сопоставимая пара имеет общий source ID, одинаковый исходный запрос, идентичную явную disambiguation/reference, совпадающие основные параметры исполнителя и формат prompt. Отдельно посчитать строгие совпадения, включая batch_size. Записать одинаковые вопросы/ответы/полные prompt: одинаковые prompt — контроль повторного стохастического продолжения, а не новая альтернатива вопроса. Не исключать одинаковые prompt из диагностики шума. Для оценки различий вопросов выделить пары с разными уточнениями; те же вопросы с иными ответами показывать отдельно.

Сохранить все denominators: активные и неактивные строки, null-goal, несовпадения, пропуски, пересечения и union исходных задач. Заморозить файл eligible pairs и exclusions до outcome analysis. Нельзя менять эту выборку после просмотра verdict без отдельной amendment и sensitivity.

## Смысловой разбор до outcome analysis

Выбрать до24 source IDs по минимальному SHA256 от `E010-v1:<source_id>` среди имеющих хотя бы одну сопоставимую пару разных вопросов. Взять все сопоставимые ветви выбранных задач. Перемешать seed20261027; скрыть variant/source ID и исходы, показать исходный запрос, уточнение, ответ и явную disambiguation. Часть baseline/исходных вопросов уже знакома, поэтому не называть проверку полностью наивной.

Один предварительный ассистентский просмотр допустим; человеческой/межэкспертной валидации пока нет. Сохранить для каждой ветви:

- `surface_class`: прежняя рубрика E008, включая partial/ambiguous/unknown;
- `asks_user_for_final_fact`: yes/no/mixed/unclear — просит ли уточнение сообщить сам фактический ответ первоначальной задачи;
- `intent_alignment`: aligned/contradictory/unclear — текст ответа согласуется ли с явно выбранной целью; внешнюю истинность фактов этим не проверять;
- `unresolved_explicit_goal_detail`: конкретная оставшаяся деталь или null; это качественный разбор заданной цели, не доказательство уникальной идентификации среди всех возможных целей;
- краткое обоснование, `annotation_status=assistant_provisional`.

Заморозить метки до открытия новых исходов. Не переносить label полного ответа на весь смысл исходной задачи. Не считать дополнительные нерелевантные требования пользователя обязательными только потому, что агент их спросил.

## Этап2: исходы

После заморозки проверить связь final generation с judge candidate, explicit target reference с judge final_ref, бинарность verdict. Пропуски/ошибки judge оставить отдельными, показать sensitivity с границами, а не отфильтровать незаметно.

Основная таблица для каждой из6 пар: число eligible source IDs, валидных target-вердиктов, оба положительных/оба отрицательных, выигрышей A/B, средняя разность target verdict. Отдельно all compatible, different-question, identical-complete-prompt и strict-batch subsets. Не объявлять лучшую variant новым методом, не суммировать6 пар как независимые задачи, не выполнять p-value fishing. Пока анализ только описательный, без причинных доверительных интервалов.

Дополнительная проверка: normalized exact match final generation против любой текстовой формы явного target answer (lowercase, ASCII punctuation removal, English articles removal, whitespace normalization). Exact match — ограниченная диагностическая метрика, не полноценная семантическая оценка. Показать расхождения с judge; несовпадение строки не доказывает неправильность. Не использовать any-reference вместо выбранной цели. Ответы с несколькими альтернативами, отрицанием или объяснениями требуют отдельного смыслового анализа.

Смысловой разбор24 задач связывается с исходами только как иллюстрация/диагностика, без вывода о распространённости механизма. Из-за фиксированного маленького неслучайного набора variant, policy selection и отсутствия known propensities IPS недопустим. Нет verified no-question branch, поэтому не оценивать абсолютную ценность уточнения относительно отсутствия вопроса.

## Решение

Если обнаружится большой разброс исходов у одинаковых prompt, усилить требования к повторениям и RNG в новом пилоте. Если partial отражает ненужный вопрос или передачу фактического ответа, исправлять постановку, не засчитывать это как успех гипотезы. Если есть сопоставимые содержательные различия, использовать их для проектирования контролируемых ветвей с сильным простым baseline. Никаких новых модельных вызовов, обучения, платных запусков и внешних отправок в E010.
