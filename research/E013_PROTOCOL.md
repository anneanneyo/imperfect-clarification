# E013: ценность вопроса для локального языкового исполнителя

27 октября2026. До первой генерации. E011/E012 и их отрицательные результаты известны. Это development-проверка конечного выбора маленькой моделью, **не новая архитектура, не обучение H3, не полный τ³ benchmark**.

## Проверяемый вопрос

Совпадает ли вопрос, полезный идеальному символическому решателю, с вопросом, после которого конкретная языковая модель чаще выбирает нужный заказ? CLEAT уже рассматривает зависимость ценности от исполнителя; наличие различия здесь не является само по себе новым вкладом. Опыт нужен, чтобы перестать оценивать сложный метод только на идеальном математическом исполнителе.

## Семьи и данные

Первые6 `development` families в сохранённом порядке E011 (стабильный SHA user_id), без выбора по модельным исходам. Для каждой — все pending orders и равномерный prior скрытой цели. Прежние imperfect probabilities и исходные цели неизменны.4 вопроса:order_id/contents/total/count, цена0.05; плюс no-question.

Перебрать все ненулевые наблюдения. У contents слить full_names/one_name в names с тем же списком товаров; natural reply не раскрывает внутренний тип полноты. IDK остаётся наблюдаемой репликой. Одинаковый полный prompt исполняется один раз, независимо от того, сколько целей его порождают. Все вероятностные массы суммируются при оценке. До генерации сохранить pack, manifest, rendered prompts, probability vectors и их хеши. Если получится более400 уникальных prompt, остановиться на design review до генерации, а не отбирать удобные ветви.

## Видимый контекст

Модель получает каталог своих pending orders: условный labelA…G, настоящий synthetic order number, имена товаров с повторениями, количество и сумму. Система сообщает, что до ответа пользователя заказы равновероятны. Исходная просьба: отменить один из этих заказов. В ветви clarification история дополняется одним фиксированным вопросом и ответом.

Шаблоны: номер — `The order number is ...`; сумма — `The total was $...`; количество — `There were ... items`; состав — `Items I remember: ...`. Последний не утверждает, что список исчерпывающий. IDK формулируется применительно к конкретному вопросу. Эти реплики **созданы нами из прежнего канала**, не человеческие ответы и не результат новой модели симулятора.

Скрытая цель, истинный alpha, probability vectors, эталон выбранного заказа, внутренние full/partial теги не входят в prompt. Модель должна выбрать один label без дополнительного вопроса. Это принудительный одноходовой decoder; его отказ/неспособность выполнить формат не скрывается.

## Исполнитель и воспроизводимость

Предварительно выбран доступный локально по ресурсам `mlx-community/Qwen3-4B-Instruct-2507-4bit`, revision `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`; основной safetensors SHA256 `2a73c6c248601ab904e035548abd8e6abb65ea27dcb5f342fb0a8910eb44173f`. Community quantization, не официальное воспроизведение full-precision Qwen. Runtime `mlx-lm==0.32.2`, полный dependency lock сохранить после установки. AppleM3/16GiB. Модель загружается из локальных файлов, без remote code и API вызовов.

Greedy decoding temperature0, max_tokens64, фиксированный seed20261027, одна генерация на unique prompt. Проверить длину до запуска, максимум4096 input tokens; длинный prompt не обрезать молча. Максимум400 генераций и общий runtime budget30 минут. Одинаковые условия и шаблон для всех ветвей. Граничное завершение по времени/ошибке отражается missing, не нулём и не выборочной заменой. Single greedy run не доказывает побитовую воспроизводимость на иных устройствах.

Парсер: допускается ровно JSON-объект `{"order":"A"}` с единственным ключом order и допустимым label; разрешена одна внешняя markdown code fence json. Дополнительный текст/ключи, invalid label, отсутствие объекта — invalid, с сохранением raw output. Нельзя извлекать удобную букву regex или повторять ответ до успеха. Max-token output сохраняется и помечается; корректный JSON с завершением по cap рассмотреть отдельно, а не объявлять обычным завершённым ответом.

## Метрики и baselines

Для фиксированного greedy executor подсчитать точную ожидаемую вероятность выбрать скрытую цель: sum по goal и response probabilities. При valid label результат0/1, invalid=0 в основной метрике, доля invalid отдельно. Runtime failures/missing не приравнивать к bad model answer: показывать границы0…1 для отсутствующей массы.

Сравнить no-question, always-contents, entropy, symbolic-EVSI и executor-aware oracle. Первые symbolic selectors используют только прежний заданный канал и Bayes endpoint; последний использует все фактически полученные ветви этой модели и потому **привилегирован**, не learned policy. Для каждого selector одинакова цена0.05; no-question0. У oracle допускается no-question при большей чистой полезности. Tie-break прежний: no-question, затем порядок четырёх вопросов.

Усреднять6 семей поровну, цели внутри семьи поровну. Сохранить все per-family/per-question значения и raw outputs, не только победителя. Никаких p-values/публикационных confidence claims по6 development случаям. При незавершённых ветвях не ранжировать oracle как установленный факт; сохранить интервальные границы.

## Связь с конечным действием

Для valid label существует однозначное соответствие synthetic order_id. Проверить это соответствие и применить отмену в свежей копии DB для каждого уникально выбранного заказа. Сравнить результат с проверенным E011 state hash для этого заказа. Правильным конечным компонентом считается состояние отмены скрытого целевого заказа. Остальные части retail-политики, включая подтверждение и пользовательские ответы, не оцениваются: **это выбор + локальный state component, не полный агентный успех**.

## Решение

Если все простые selectors уже близки к oracle, не обучать сложную модель на этих6 семьях. Если появляется gap, сначала разобрать формат, числовое/предметное сопоставление и случаи недоопределённой реплики. Не считать исправление формата нейросетевым вкладом. Только устойчивое содержательное различие оправдывает подготовку более широкой learning-проверки с одинаковым feedback и новым тестом. Внешних отправок и платного inference нет.
