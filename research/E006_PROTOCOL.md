## Проверяемое утверждение

Можно ли использовать публичный checker ClarifyBench как измеритель точности последовательности tool calls? Отдельно различаем точное совпадение вызовов, полноту покрытия эталонных вызовов, долю совпадений имён/параметров и фактический успех конечного состояния. Последнее в этом эксперименте **не измеряется**.

Проверяем версию `a85d4f9df1fc87d05c713fd408f8a57d72bcc348` репозитория `MananSuri27/ClarifyBench`. Все 602 непустых сценария A/E/I участвуют в проверке; два пустых JSON фиксируются отдельно. `sample/` не добавляется, так как дублирует основной набор. Это 602 синтаксические тестовые записи, не 602 независимых пользовательских эксперимента.

Для запуска нужны только typing и стандартные встроенные функции Python. Чужие исходники и dataset в наш репозиторий не копировать.

## Как строятся записи

Для каждой gold-последовательности строим совместимый `simulation_result`: `final_tool_calls` с теми же именами и аргументами, `all_tool_call_attempts` с `was_executed=True, success=True`, пустая история разговора. Эти флаги **искусственно заданы**, а не подтверждены выполнением инструментов. Для infeasible-задач это также только проверка синтаксической самосогласованности checker; корректные gold calls могут описывать невозможные действия.

Все изменения детерминированы сортировкой пути и индексов. Сохраняем хеш исходной/изменённой последовательности и идентификаторы, не полное содержимое внешних calls. На всех применимых заданиях проверяем:

1. `gold`: неизменённые эталонные вызовы. Структурная exact equality должна быть True.
2. `delete_first`: удалить первый вызов. Однозначное нарушение полноты/числа вызовов; exact equality должна быть False. Coverage может не упасть при повторных идентичных вызовах — это отдельно измеряем.
3. `duplicate_first`: добавить копию первого вызова. Exact equality False; полнота покрытия по смыслу может оставаться 1.
4. `extra_action`: добавить отсутствующий в gold вызов с именем изменяющего состояние инструмента своего домена, выбранного из опубликованных gold других сценариев. Параметры копируются из выбранного публичного вызова. Это **симулированная лишняя операция**, её применимость/опасность в данной конфигурации не проверяется. Exact equality False, coverage может остаться 1.
5. `wrong_parameter`: в первом вызове с параметрами заменить один аргумент заведомо отсутствующим маркером. Exact equality False. Если исходных параметров нет, случай помечается неприменимым и не исчезает из знаменателя незаметно.
6. `reverse_order`: обратить порядок вызовов, если последовательность действительно меняется. Проверяем отдельно ordered equality и unordered multiset equality. Не объявляем любую перестановку ошибкой задачи: независимые действия могут коммутировать. Это тест чувствительности метрики к порядку.
7. `failed_attempt`: добавить к корректным final calls отдельную неуспешную попытку. Exact equality final calls True, execution success должна быть False; отличаем след от корректного восстановления после временной ошибки.
8. `drop_repeated_identical`: удалить один из полностью одинаковых gold-вызовов, когда такой есть. Exact/multiset equality False; диагностирует повторное использование одного actual match для нескольких gold.
9. `replace_duplicate_with_extra`: вместо одного повторного полностью одинакового вызова вставить лишнее действие из пункта 4, сохранив общее число вызовов. Exact/multiset equality False; проверяем, достаточно ли штатной проверки длины списка для обнаружения пропуска и подмены.

Отдельная контрольная семья из **собственных** маленьких вызовов: два одноимённых инструмента с разными аргументами; два идентичных вызова; правильная последовательность с лишним действием; перестановка зависимых по нашей искусственной семантике действий `set_value(1) → set_value(2)`; отсутствие всех действий; неуспешная попытка перед правильным финалом. Для последнего примера считаем итог простейшего собственного состояния, не выдавая его за state checker ClarifyBench.

## Метрики, проверки и артефакты

По каждой записи сохраняем: применимость, исключение при расчёте (если было), штатные correctness.exact_match, tool_match_rate, param_match_rate, coverage_rate/coverage_success, execution.execution_success и общий success. Отдельно считаем наши строгие ordered и multiset совпадения имён/аргументов. Они служат логическим диагностическим ориентиром, **не исправленным официальным benchmark score**.

Сводки: число запланированных/применимых/неприменимых/выполненных/упавших проверок; показатели отдельно A/E/I и по мутации; число gold self-consistency failures; случаи, где coverage=1 при лишних/пропущенных действиях; чувствительность к порядку. В каждом домене сохранить идентификаторы репрезентативных fixtures, всего не менее 12 и не менее трёх с повторными инструментами. Никакие ошибочные эпизоды не выбрасывать из отчёта.
