# E007 — проверка конечного состояния в retail τ³-bench

27 октября 2026. [Протокол](E007_PROTOCOL.md) записан до исполнения; [независимый review](E007_REVIEW.md) завершён.

**Результат:** получили воспроизводимый компонент проверки конечного состояния внешней среды. Он принимает разные последовательности с одинаковым результатом и замечает пропущенные/лишние изменения. Это позволяет двигаться к агентному пилоту, но **не означает, что внешняя оценка агента выполнена**: диалог, соблюдение правил и LLM judge ещё не запускались.

Источник: [τ³-bench v1.0.1](https://github.com/sierra-research/tau2-bench/tree/fc0055dc4e0a316c3f83133267fbd6faaa770992), MIT, commit `fc0055dc4e0a316c3f83133267fbd6faaa770992`. Намеренно закреплён исторический релиз; текущая main уже другая. Проверены 114 retail-задач, авторские train74/test40. От этого они не становятся новым закрытым тестом для нашего исследования.

## Что исполнялось

Из просмотренных исходников извлечены AST-определения Pydantic models, DB и доменных tools; исходные тела методов не изменены. Сохранены метакласс, декоратор, доступ к toolkit и диспетчер `use_tool`. Пропущены пакетные imports, schema/prompt helpers, агент, сетевые клиенты, orchestrator и judges. Все изменения происходят в копии DB в памяти. На каждый replay создаётся новая копия исходного JSON, затем Pydantic-модель. Сравнивается всё сериализованное состояние базы по SHA256 — это собственная реализация проверки равенства состояния, не побитовое воспроизведение формата штатного reward.

99 из 114 reference-последовательностей не дали исключений, в 15 были ошибки отдельных вызовов. **Эти 15 нельзя назвать неуспешными задачами.** В ряде сценариев пользователь сначала сообщает неверный идентификатор/email, затем исправляет его. В 64 после неудачного exchange идёт успешный modify_pending — fallback является частью reference. 13 из 15 содержат только ошибки READ-вызовов; два — ошибки WRITE. Replay продолжает обработку после исключения, как gold-путь штатного evaluator.

Все 114 воспроизведены дважды с одинаковыми состояниями и ошибками. В 103 конечная DB отличается от начальной, в 11 — нет. Это состав эталонных сценариев, а не качество no-ask агента. Для задач чтения/отказа пустой план может сохранить DB, но не выполнить требования к разговору.

## Проверка на контролируемых изменениях плана

12 fixtures выбраны из train до исполнения: первые по стабильному SHA от ID среди задач с WRITE. В них намеренно остался один reference с ошибкой READ; задачи не отбирались по успеху. Выполнены все 96 запланированных мутаций, пропусков нет.

| Вариант | Та же конечная DB / 12 | Все вызовы исполнились / 12 |
|---|---:|---:|
| Пустой план | 0 | 12 |
| Только WRITE из reference | 12 | 12 |
| Пропустить первый WRITE | 0 | 11 |
| Подменить ID первого WRITE несуществующим | 0 | 0 |
| Добавить READ | 12 | 11 |
| Добавить незапрошенное изменение адреса | 0 | 11 |
| Перевернуть порядок | 12 | 11 |
| Повторить первый WRITE | 12 | 2 |

Проверка результата не требует дословного воспроизведения вспомогательных READ-вызовов. Эквивалентность WRITE-only — **привилегированный контроль с готовыми аргументами**, а не возможность обычного агента обходиться без чтения. Перевёрнутые последовательности эквивалентны в этих 12 случаях; общая независимость от порядка из этого не следует. Повторный WRITE часто отклоняется инструментом и потому оставляет ту же DB: необходимо отдельно учитывать ошибки/правила, если они важны для итогового контракта.

## Два конкретных ограничения релиза

1. У 5 задач (20, 21, 36, 37, 100) после `modify_pending_order_items` обнаружены 9 реально изменённых items с price/options от последнего `variant` в цикле. Независимый побъектный анализ подтвердил все 9; это не сравнение исторических цен с текущими. Причина видна в [методе tools.py](https://github.com/sierra-research/tau2-bench/blob/fc0055dc4e0a316c3f83133267fbd6faaa770992/src/tau2/domains/retail/tools.py): цикл изменения items использует значение `variant`, оставшееся от предыдущего цикла. Gold и агент могут быть одинаково затронуты этой семантикой, поэтому совпадение DB не доказывает корректность самой модели магазина. Upstream не исправлялся.
2. У задачи105 единственный gold-exchange отклонён из-за недостаточного баланса указанной gift card, а NL assertion требует обменять оба предмета. Это локальная несогласованность reference и текстового критерия; не вывод о непригодности всего набора. Нужен отдельный разбор допустимого платежа/цели перед включением задачи в основной пилот.

Проверка metadata была усилена после независимого review: сравнение по `new_id` заменено наблюдением тех объектов, которые действительно изменились. Это validation repair против ложных срабатываний на дубликаты, записанный в протокол; повтор сохранил все агрегаты.

## Решение для проекта

У retail есть пригодная основа для execution-based outcome. Однако официальный reward у 112/114 задач включает DB+NL_ASSERTION (40 имеют непустые assertions), у двух — DB. Только нашу проверку DB нельзя выдавать за полный task success, а неправильные ответы/отсутствие подтверждения автоматически считать правильными из-за совпадения состояния.

Не менять тему на ремонт benchmark. Для следующего небольшого модельного пилота: заранее определить критерии пригодности, проверить независимые postconditions изменённых объектов и полный reward contract, отделить известные несовместимости. Сохранить официальный score и наш дополнительный строгий анализ отдельно. До этого не обучать selector на этих labels и не объявлять независимую проверку H3 законченной.

Одновременно E008 исследует готовые тексты уточнений из другого опубликованного корпуса: он нужен для проверки самого несовершенного канала ответа, который этот state probe не проверяет.

## Воспроизведение

`python3 experiments/tau3_retail_state_probe.py --repo <checkout-v1.0.1>` — Python3.12, Pydantic2.14.0; локально использован bundled runtime без установки пакетов. Скрипт проверяет commit и SHA256 восьми исходных файлов. Изменённый checkout отвергается.
