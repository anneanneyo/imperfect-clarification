# E011: проверяемая цепочка «неполный ответ → выбор заказа → отмена»

27 октября 2026. Записано до вычисления ценностей вопросов и исполнения новых ветвей. Известна только инвентаризация закреплённой retail DB: 500 пользователей, 1000 заказов, 423 pending; 100 пользователей имеют от 2 до 7 pending orders. Это **инженерный и математический пилот на внешней базе**, не официальный τ³ benchmark, не опыт с людьми и не проверка нового обученного метода.

## Зачем

После E010 не обучать selector на непроверенном свободном judge. Вместо этого проверить полностью наблюдаемый экспериментатором контракт: сохранение цели, частичные правдивые сведения, Bayes, выбор конечного действия и проверка реального состояния инструментов. Симулятор и вероятности здесь заданы нами; эффекты не доказывают распространённость проблемы у людей или LLM.

## Данные и цель

Использовать ту же DB и неизменённый cancel_pending_order из τ³ v1.0.1, commit `fc0055dc4e0a316c3f83133267fbd6faaa770992`, хеши из E007. Включить всех пользователей с ≥2 pending orders, без отбора по outcome. Задача каждой семьи: отменить ровно один скрыто выбранный pending order; причина фиксирована `no longer needed`. Это новая конструкция на базе среды, а не подмена исходных 114 benchmark tasks.

Пользователь/принадлежащие ему pending orders уже найдены через доступные сведения. Их состав, цена и число товаров доступны selector; скрыт только нужный пользователю заказ. Равномерный prior по pending orders — заданное допущение, не learned prior. При равенстве posterior выбрать лексикографически первый order ID. По стабильному SHA256 от `E011-v1:<user_id>` отметить 60/20/20 семей development/validation/reserved; этот запуск проверяет все семьи как инженерные данные, поэтому reserved после него не является закрытым финальным тестом.

## Четыре вопроса, один ход и отсутствие вопроса

Стоимость каждого вопроса c из {0,0.02,0.05,0.10}. После одного ответа нужно выбрать заказ; дополнительный информационный ход не разрешён. Сравниваются конечная вероятность выбора нужного заказа и она же минус c.

1. `order_id`: назвать номер. Верный номер с вероятностью0.35, иначе IDK.
2. `contents`: перечислить товары. Полный мультимножество имён с вероятностью0.45; частичное указание одного равномерно выбранного **уникального имени** с0.45; иначе IDK. Полный и частичный ответ имеют разные наблюдаемые теги, поэтому «назван один из товаров» не означает «в заказе только этот товар». Сохраняются количества повторяющихся товаров в full.
3. `total`: сумма цен позиций с округлением до центов. Верное число с0.60, иначе IDK.
4. `count`: число позиций. Верное число с0.90, иначе IDK.

Названные вероятности — искусственный контроль, выбранный до результата. Не подгонять их после расчёта. Два режима: `perfect` (всё всегда полно) и `imperfect` (как выше). Стоимость не изображает измеренную человеческую нагрузку. Неопределённость и частичность разрешены, ложь/изменение скрытой цели запрещены. Никаких сведений сверх заданного заказа.

## Методы и метрики

Все методы используют одинаковые фиксированные priors/среду. No-ask — выбрать MAP prior. `always_id` — всегда вопрос1. `random_question` — равномерно выбрать один из4 вопросов. `entropy` — вопрос с максимальным ожидаемым уменьшением энтропии, no-ask только при нулевом gain. `oracle_evsi` — лучший вопрос по ожидаемой вероятности правильного конечного решения минус стоимость, сравнить с no-ask. При равенстве EVSI остановиться; между вопросами порядок order_id, contents, total, count.

Основной расчёт — точное суммирование всех целей и всех возможных наблюдений, без Monte Carlo. Posterior вычисляется по K(y|goal,q), включая неполные ответы. Отдельная диагностика: после частичного ответа сравнить истинный posterior с равномерным распределением по совместимым заказам; показать максимальную разность вероятностей и последствия для выбора. Это иллюстрация корректного likelihood, не новая теорема и не обучаемое преимущество.

Каждая семья имеет равный вес; внутри семьи равный вес имеют цели. Не взвешивать семьи пропорционально числу заказов. Сохранить все результаты по семействам и все4 цены; не выбирать удачную цену. Не считать oracle_evsi обученным методом, не подавать истинный K будущему learner под видом наблюдённых данных.

## Проверка исполнения

Для всех включённых pending orders выполнить ровно одну отмену в свежей копии DB, через просмотренные доменные tools E007. Проверить независимо: отменён только выбранный заказ; другие orders/products неизменны; исходные payment entries сохранены; добавлены соответствующие refunds; gift-card balances изменены согласно возвращённым платежам, остальные пользовательские поля неизменны. Ошибки и несоответствия сохранить, не исключать задачи по результату. Если cancellation component не исполняется на всех, не отождествлять selection accuracy с execution success.

Это проверка **компонента решения и изменения состояния**. Полная политика retail отдельно требует диалога и подтверждения конкретного действия; здесь они не симулируются и не получают положительную оценку. Будущему агенту потребуется отдельный контракт подтверждения, причём информационную ценность такого хода нельзя скрыто давать no-ask baseline.

## Обязательные проверки и результат

- Все K неотрицательны и нормированы; ненулевые observations совместимы со скрытой целью.
- Perfect ID однозначно решает выбор; no-ask имеет accuracy1/n; EVSI не хуже no-ask и любой одноходовой альтернативы при данном K и цене.
- Переход к несовершенному каналу не повышает oracle-accuracy для того же вопроса (это заданное огрубление полного ответа).
- Отдельный маленький аналитический пример проверяет likelihood частичного ответа с разным количеством имён; не тестировать лишь копию той же функции.
- Все файлы источника и протокол хешируются. Новых LLM/API-вызовов, моделей, обучения и внешних действий нет.

Выход: воспроизводимый пример с понятными данными и итоговыми действиями, числа по простым методам и честная граница доказанного. Если EVSI преимущество отсутствует, сохранить нулевой результат. Дальше — решать, какая наблюдаемая граница знания пользователя и какой ограниченный feedback оправдывают обучение; не объявлять успех H3 по oracle.
