# UserBench: кандидат для независимой среды, с явным адаптером оценки

8 ноября 2026. [Статья](https://aclanthology.org/2026.emnlp-main.772/), [закреплённый код](https://github.com/SalesforceAIResearch/UserBench/tree/80506d2ab484cab843e60a2401ff3e0290d05b87), [протокол E024](E024_PROTOCOL.md), [результат](../results/userbench_contract_e024/summary.json).

UserBench предлагает задачи выбора туристических вариантов по неявным предпочтениям пользователя. Это кандидат на проверку нашей темы в другом домене. Прочитаны аннотация, введение, разделы 3.1–3.3 и фрагменты приложений о симуляторе и настройках. Статья опубликована в EMNLP 2026. Полного воспроизведения нет; данные train/test и профили в этом блоке не загружались.

## Проверка исходного кода

Прочитаны README, config, загрузчик задач, функции исполнения, маршрутизации ответов и существенные части eval.py. Версия: `80506d2ab484cab843e60a2401ff3e0290d05b87`. Следующие выводы получены из кода и локального контракта, а не из заявленных результатов статьи.

1. Среда начисляет отдельные награды за поиск, выявление предпочтения и выбор варианта. Их сумма не равна качеству конечного решения. Для нашего сравнения нужна отдельная метрика по выбранному option ID, с одинаковым бюджетом вопросов/поисков.
2. Генератор сначала выбирает тип вопроса и ID предпочтения, потом формирует ответ. Успех выявления отмечается по этой ветке, без отдельной проверки смысла полученного текста. Поэтому промежуточную награду нельзя использовать как доказательство того, что ответ передал нужную информацию.
3. Синхронный `step` завершает one-choice-задачу после выбора по каждому аспекту. В `step_async` этой проверки нет: остаются достижение всех best options или лимит шагов. Поставляемый eval.py использует асинхронный путь.
4. Полная структура `info` содержит скрытые сведения. В просмотренном rollout к сообщениям модели добавляется feedback, а не весь info. Утечка через этот путь не установлена. Начальные сообщения из parquet не проверены: адаптер должен отдельно контролировать весь видимый вход.
5. Ответ о несуществующем или уже выявленном предпочтении отличается от незнания существующего предпочтения. Прямое переименование этой ветки в наш unknown-channel было бы неверным.

Ссылки на реализацию: [reward и варианты ответа](https://github.com/SalesforceAIResearch/UserBench/blob/80506d2ab484cab843e60a2401ff3e0290d05b87/travelgym/env/prompts.py), [step/step_async](https://github.com/SalesforceAIResearch/UserBench/blob/80506d2ab484cab843e60a2401ff3e0290d05b87/travelgym/env/travel_env.py), [rollout](https://github.com/SalesforceAIResearch/UserBench/blob/80506d2ab484cab843e60a2401ff3e0290d05b87/eval.py).

## E024: выполненная проверка

Без импорта пакета извлечены неизменённые AST функций из трёх проверенных по Git blob SHA файлов. Вручную задан один hotel-aspect: H1 лучший, H2 допустимый, H9 неверный. Выполнено 12 коротких траекторий: три выбора × два интерфейса × режим повторений, затем попытка выбрать H1.

| Режим одного выбора, первый выбор | Награда | Sync завершён | Async завершён |
|---|---:|---|---|
| Лучший H1 | 1,0 | да | да |
| Допустимый H2 | 0,8 | да | нет |
| Неверный H9 | 0,0 | да | нет |

В последних двух асинхронных случаях дальнейшая попытка H1 запрещена правилом одного выбора, но эпизод ещё открыт. При разрешённых повторениях оба интерфейса продолжают работу после H2/H9. Проверка показывает различие на fixture; его влияние на опубликованные результаты не измерено.

Отдельно ответ генератора искусственно заменён на `I don't know.` при маршрутизации к P1. Среда выдала 0,2 и перенесла P1 в выявленные предпочтения. Это воспроизводимый условный контрпример к семантической гарантии награды, не наблюдение частоты ошибки реального симулятора.

Сетевых/model вызовов во время исполнения функций: 0; benchmark-задач: 0. Исходники загружены отдельно. [Код проверки](../experiments/userbench_contract_e024.py), [все траектории](../results/userbench_contract_e024/trajectories.json), [закрепление файлов](../results/userbench_contract_e024/manifest.json).

## Решение

Допустить UserBench к небольшому аудиту **официального train**, но пока не к обучению или финальному сравнению. Сначала: проверить начальный видимый запрос и разметку вариантов, отделить отсутствие предпочтения от отсутствия знания, задать финальную метрику и явное правило остановки. Только после этого оценивать разнообразие случаев, где возможный ответ меняет лучший вопрос. Синтетически добавленный нами канал ответов должен называться модификацией UserBench, а не воспроизведением исходного benchmark.

Обнаруженные особенности среды сами по себе не являются научным вкладом нашего проекта. Исходная цель — полезность уточнений при несовершенных ответах — сохраняется.
