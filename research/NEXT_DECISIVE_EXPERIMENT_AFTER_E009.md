# Следующая решающая проверка после E009

27 октября 2026. Основная тема сохраняется: выбирать уточнение по уменьшению ошибки конечного решения, учитывая несовершенный ответ. Этот документ задаёт порядок работ; это не заявление о выполненном эксперименте и не заранее зарегистрированный итоговый тест.

## Какой вопрос теперь проверять

**Меняется ли конечное решение из-за содержания/неполноты ответа, если исходная задача, скрытая цель и исполнитель остаются одинаковыми?** Если нет, или эффект объясняется плохим вопросом/судьёй, усложнение оценивателя ценности не обосновано. Наличие фразы IDK само по себе ничего не решает.

## Этап A — использовать сохранённые ветви, если они сопоставимы

Проверить опубликованные BAG-конфигурации одного assistant model, начиная с Qwen3-8B. Приоритет — фиксированный `final_prompt=prompt`, неизменный симулятор Gemini2.5Flash, data_seed50, варианты reasoner prompt `belief`, `prompt`, `belief6`, `belief7`, **если соответствующие файлы реально опубликованы**. Все реально доступные варианты перечислить до просмотра новых исходов; не оставлять только удачные. Уже прочитанный baseline из E008 считать development-материалом.

Первичная инвентаризация выполнена после записи этого плана: все12 ожидаемых user/final/judge файлов для четырёх вариантов присутствуют в закреплённой ревизии. [Метаданные доступности](../results/fixed_executor_feasibility/availability.json) сохранены до загрузки новых outcomes. Содержательная сопоставимость ещё не проверена; наличие файлов само по себе её не доказывает.

Сначала только инвентаризация и связывание:

- совпадают source ID, исходный запрос и выбранная явная disambiguation;
- совпадают модель и параметры финального исполнителя, его системная инструкция и правило формирования контекста;
- различаются проверяемые вопросы/ответы; совпавшие ветви не считать дополнительными независимыми примерами;
- доступны raw output, target reference и judge, с отдельным учётом отсутствующих/испорченных результатов;
- фиксируется вся пересекающаяся и непересекающаяся популяция. Сравнение только пересечения имеет ограниченную целевую популяцию.

Варианты с `disambiguation=null` не использовать как подтверждение одной и той же скрытой цели без отдельного смыслового обоснования. Латентная цель доступна только аудитору/оценщику, не selector. Если target refs между direct/no-question и clarified ветвями различаются, не считать разницу их scores ценностью уточнения.

До вскрытия новых outcomes заморозить eligible IDs, причины исключения, классы качества вопроса/ответа и точное правило метрики. Для небольшой диагностической выборки проверить final answers по явной цели независимо от опубликованного судьи. Предварительные assistant labels не заменяют человеческую валидацию публикационного эксперимента.

Выход A: таблица фактически сопоставимых пар с объяснением, что они идентифицируют. Разница единичных стохастических продолжений — шумная реализация, а не точная ожидаемая ценность. Поведенческие вероятности не известны, рандомизированного назначения вопросов нет: не использовать IPS и не объявлять обобщённый причинный эффект. Если сопоставимых ветвей нет, это конкретный результат о недостающем дизайне, а не основание добавлять искусственный эффект.

## Этап B — спроектировать недостающие ветви

Если A выявит содержательные случаи, сформировать небольшой новый пилот до масштабного обучения:

1. Фиксированные задача, скрытая цель, набор кандидатных вопросов, исполнитель и бюджет. Добавить действие без уточнения.
2. Канал ответа должен отражать реальную границу доступного пользователю знания/предпочтений. Отдельно валидировать правдивость, полезность и отсутствие выдачи эталонного решения. Различать «не знаю» и «мне всё равно».
3. Продолжения одного исполнителя после каждого ответа; одинаковые условия и достаточные повторения для оценки шума. Если берётся ограниченный feedback, одинаковые журналы и вычислительные бюджеты для всех learners.
4. Сравнения: no-ask, простой answerability-aware EVSI, прямой value estimator, отдельная модель ответа с оценкой исхода. Oracle только как верхний ориентир, с явно раскрытой недоступной информацией. Сопоставить выбранную постановку с CLEAT, CLARITI и Model-Free PE.
5. Главная метрика — конечная ошибка/полезность при одинаковом вопросном бюджете. Стоимость самого вычисления ценности также учитывать. Разбиение по исходным задачам и связанным целям, не по репликам.

Для независимой агентной проверки кандидат — закреплённый retail τ³ с уже проверенным state-компонентом E007. До модельного запуска нужен полный контракт успеха: изменения состояния, чтение/ответы, подтверждения, правила; DB-match отдельно от полного score. Известные несогласованности релиза учесть заранее, не исключать задачи по результату модели. Это новый пилот, он пока не выполнен.

## Условия изменения решения

- Если простой метод после честной настройки не уступает факторизации, не масштабировать сеть ради желаемого вывода.
- Если эффект вызван вопросом о ненужной детали или ошибкой evaluator, устранить эту причину в постановке, не переименовывать её в преимущество моделирования partial.
- Если информационная часть полезна, но исполнитель не умеет пользоваться ответом, разделить измерение ценности информации и ценности для данного исполнителя.
- Для статьи нужен проверенный вклад относительно литературы, воспроизводимый результат и независимая проверка. Сейчас эти условия полностью не выполнены.

Продолжение A возможно без нового бюджета на модель. Новые модельные запуски потребуют конкретного воспроизводимого runtime/доступа; отсутствие такого доступа сейчас не останавливает A и смысловой анализ. Работа с файлами и исследовательские решения продолжаются автономно. Отправка статьи или сообщений от имени Ани не выполняется автоматически.
