# E014: внешний текстовый replay Lavoir с фиксированным исполнителем

27 октября 2026. Протокол до новой выборки и генераций. E013 и source gate известны. Development-диагностика; не новый метод, не тест опубликованной модели Lavoir и не полная агентная среда.

## Выборка и семантическая проверка

Закреплённый banking_support train из Lavoir revision d2c66dc86c782fadccc14748d8fa073ca16a6090, SHA256 файла 6641c847f59d539fc99de6dae24f92babeb0358c68699514528e23f3c8c71365. Исходный case_id — первые три компонента ID. Все 486 case-групп ранжировать SHA256("E014-v1:" + case_id), взять первые 24, внутри взять все kind=a профили. Не выбирать по gold, oracle или модельному результату. Веса: case 1/24, профиль 1/n внутри case. Это выбранное распределение наблюдаемых примеров, не исходный prior генератора.

До генераций сохранить все source rows и хеши. Ассистент читает уникальные начальные сообщения и пары вопрос–ответ с evidence/reveal/profile, помечает соответствие: supported, unclear, contradiction. Структурная проверка проверяет reveal и gold по schema; она не заменяет смысловую. Метки ассистента не считать человеческой валидацией. Исходные тексты не исправлять. Если есть противоречия или неясности, сохранить конкретные строки; не выкидывать после исходов. При существенной несовместимости содержания с gold остановить запуск для пересмотра постановки до генерации. Малые неясности допускают основной replay с отдельной чувствительностью по заранее отмеченным примерам; исключения всегда раскрыть.

## Исполнитель и доступная информация

Qwen3-4B-Instruct-2507-4bit, revision 50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b; MLX-LM0.32.2, среда и файлы модели из E013. Все локально, remote code выключен. Greedy temperature0, seed20261027, max_tokens64, input<=4096, не больше600 уникальных prompts и30 минут runtime. Один вывод на каждый точный prompt. Ошибки не перезапускать ради успеха, missing не приравнивать к неверному модельному решению. Сырые выводы сохранять.

Системное сообщение раскрывает полный порядок правил банковской маршрутизации и допустимые классы. Он одинаков для всех ветвей. Модель получает исходный user text, а в ветви вопроса — опубликованные question/answer. Доступны только правила и эти реплики. Не доступны ID, gold, profile, posterior, evidence, reveal, answer_kind, oracle_voi. При недостатке информации всё равно выбрать один класс. Полный prior исполнителю не сообщается; это явно ограниченный языковой decoder, а не Bayes solver.

Выход — единственный JSON ключ team, значение из cards/fraud/loans/accounts/complaints. Разрешена одна внешняя json code fence; duplicate keys, extra keys/text и недопустимые значения — invalid, без извлечения удобного ответа из текста. Invalid=0 основной метрики. Отдельно length-termination, runtime errors/missing и интервальные границы их вклада.

Перед первой генерацией сохранить rendered prompts, токены, связанные source IDs, метки проверки, зависимости, code/protocol hashes. Точный prompt с одинаковыми текстами исполняется один раз, результаты переиспользуются для всех соответствующих профилей. Условия не меняются после исходов.

## Ветви и показатели

Для каждого исходного профиля no-question и все5 опубликованных probes: issue/product/money_gone/compensation/customer_name. Одна сохранённая реплика на вопрос — один наблюдаемый исход. Полного ожидаемого EVSI и распределения ответов эти ветви не дают.

Правильность — совпадение выбранного отдела с gold, уже независимо проверенным по полным правилам. Цена вопроса0.05. Сохранить per-row/per-question accuracy, utility и форматные исходы. Усреднять по заранее заданным case/profile весам.

Сравнения: no-question; каждый фиксированный вопрос; uniform-random question; лучший фиксированный вопрос после просмотра исходов (описательный post-hoc ориентир); oracle по скрытому профилю (после исходов выбирает одну из6 ветвей); oracle с одинаковым выбором для идентичных доступных входов (исходное сообщение+одинаковые правила). Последние два — привилегированные post-hoc ориентиры на наблюдённых ответах, не обученные policies. Tie-break: no-question, затем issue/product/money_gone/compensation/customer_name с tolerance1e-12.

Для symbolic diagnostic использовать уже заданные source posterior и reveal как явно привилегированный semantic oracle: выбрать наиболее вероятный класс по schema, tie-break в порядке schema units. Он отделяет потери языка от неопределённости, но не является доступной языковой baseline. Его вероятность на оставшейся неоднозначности не называть истинной человеческой вероятностью.

Никаких p-values по24 development cases. Никакого выбора удачных seed/переформулировок. Тестовые данные Lavoir не читать. Повторная обработка результатов допустима для проверки расчётов, но не новые генерации под видом первой попытки.

## Решение после анализа

Если лучший фиксированный вопрос близок к oracle одинакового видимого входа, не обучать сложный selector. Если остаётся содержательный запас, разобрать, связан ли он с целевой информацией, ошибками исполнителя, отвечаемостью или артефактами текстов. Не считать разрыв до скрыто-профильного oracle обучаемым преимуществом без проверки наблюдаемости. Только после этого планировать одинаковый feedback для direct/factorized/simple и новый закрытый тест. Новизна не следует из одного diagnostic gap.
