# ClarifyBench: можно ли проверять конечный результат без LLM

27 октября 2026. Проверен filesystem-домен GFS из публичного [ClarifyBench](https://github.com/MananSuri27/ClarifyBench), commit `a85d4f9df1fc87d05c713fd408f8a57d72bcc348`. Код прочитан до исполнения. Все операции происходили над объектами в памяти; файлы пользовательского компьютера GFS не меняет. Новых библиотек, моделей, API и сетевых вызовов во время эксперимента нет. Исходные задачи и код upstream в проект не копировались.

**Вывод:** конечное состояние в этом домене доступно и детерминировано; узкий checker для явно заданной файловой цели реализуем. Но автоматически превратить опубликованный список gold-вызовов в надёжный критерий конечного успеха нельзя. Такой список не всегда является полным исполнимым планом, а для чтения файлов одного финального состояния недостаточно. Массово чинить этот benchmark ради основного эксперимента сейчас нецелесообразно.

## 1. Какая реализация действительно исполняется

В `simulation/mock_api.py` есть MockAPIClient, который возвращает успешность/совпадение параметров и сам не моделирует файловое состояние. Однако **основной runtime main.py использует настоящие доменные plugins**:

- [main.py, строки 111–119](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/main.py#L111): инициализация GFSPlugin из `initial_config`;
- [main.py, строка 179](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/main.py#L179): ToolExecutor с plugin manager;
- [core/tool_executor.py, строка 207](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/core/tool_executor.py#L207): вызов доменного `execute_tool_with_virtual_support`.

Наш harness вызывает этот же GFSPlugin напрямую: предвалидация, удаление `<UNK>`, исполнение, остановка последовательности при первой ошибке. Это повторяет существенную для gold доменную семантику. При этом пропущены agent, LLM, registry UI, выбор вопросов, текстовые ответы и виртуальные инструменты. **Это replay домена, не воспроизведение всего агентного эксперимента.** Аудит официальной итоговой метрики проводится отдельно.

GFS хранит дерево `Directory/File` и текущий каталог. При загрузке current directory устанавливается в корень, даже если в пользовательском тексте упоминается вложенная папка. Модуль не использует часы или генератор случайных чисел; замораживать дату/seed здесь не требуется. Повтор всех gold-последовательностей на свежих экземплярах дал идентичные результаты.

## 2. Воспроизведение gold из предоставленного начального состояния

Проверены все 116 задач, у которых единственный `initial_config` — GorillaFileSystem. Sample-копии исключены. Списки вызовов исполнялись в сохранённом порядке, без ручной вставки `cd`, `mkdir` или исправлений параметров.

| Подмножество | Задач | Все gold-вызовы исполнились | Неисполняемые gold, которые проходят при другом стартовом cwd | Успешные gold без изменения файлового дерева |
|---|---:|---:|---:|---:|
| A | 39 | 22 | 9 | 9 |
| E | 43 | 25 | 10 | 11 |
| I | 34 | 21 | 9 | 8 |
| Всего | **116** | **68** | **28** | **28** |

48 последовательностей прерываются. Первые ошибки: cp — 12, mv — 10, diff — 9, cat — 7, echo — 4, wc — 3, grep — 3. Поиск другого стартового cwd — **привилегированная диагностика** по всем директориям начального дерева; эти результаты не подставлены в основной replay и не считаются исправленной оценкой. Это показывает зависимость многих списков от неявного контекста/пропущенной навигации.

Например, `ClarifyBench_A/20030cbb.json` содержит операцию копирования файла из вложенной папки, но список не включает переход туда; смена стартового cwd делает вызовы исполнимыми. В `ClarifyBench_A/9634c0b1.json` gold echo содержит дополнительный аргумент `DEFAULT`, которого нет у метода, и падает с EXECUTION_ERROR. Всего такой ключ встречается в шести GFS-задачах; не во всех исполнение доходит до него.

**Нельзя интерпретировать 68/116 как процент решённых задач агентом или процент корректности всего benchmark.** Gold может размечать важные вызовы, а не полный операционный сценарий, который агент должен восстановить самостоятельно. Результат означает лишь: эти списки без дополнительных решений не подходят для автоматической генерации конечного gold-state.

Обратное также неверно: успешность всех API-вызовов не гарантирует выполнение намерения. При ручном просмотре `ClarifyBench_A/0a9a8966.json` literal gold создаёт файлы в корне, хотя текст требует работу во вложенной папке; отсутствующая целевая директория в `cp` может интерпретироваться как имя копируемого файла, поэтому ошибки API нет. Это единичная проверка несоответствия, а не систематическая семантическая разметка всех 116 задач.

## 3. Что именно проверяли как конечный результат

Реализованы два снимка состояния:

1. **Content state:** имена и содержимое файлов/директорий, без текущего каталога и порядка вставки элементов.
2. **Operational state:** то же дерево с порядком элементов и текущим каталогом. Порядок важен: `ls` возвращает insertion order, а в данных есть запросы о первом/втором файле.

Сами строки содержимого в артефакты не попадают: сохраняются хеши. Для диагностического дополнения read-результатов считаем multiset хешей outputs от gold-операций чтения. Вариант «state + read-reference» требует успешных вызовов, совпадающего operational state и наличия всех gold read-outputs; дополнительные чтения разрешены.

**Этот составной критерий написан нами и не является официальной метрикой ClarifyBench.** Он не проверяет, рассказал ли агент пользователю найденный результат, не понимает семантическую эквивалентность текстов и не проверяет пользовательские ограничения порядка. Критерий useful для диагностики плана, но не готов как универсальный checker цели. Сравнение с одним gold-state может быть одновременно слишком строгим (лишняя безвредная навигация) и слишком слабым (сам gold не соответствует цели).

## 4. Контролируемые изменения исполнимых планов

Изменения применялись только к 68 literal-gold, которые исполнились без ошибок. Эти случаи также не объявлены автоматически семантически правильными задачами.

| Изменение | Вариантов | То же operational state | Проходит наш state + read-reference |
|---|---:|---:|---:|
| Не делать ничего | 68 | 20 | 0 |
| Добавить чтение `ls` перед планом | 68 | 68 | 68 |
| Создать лишний файл после плана | 68 | 0 | 0 |
| Перевернуть порядок вызовов | 68 | 34 | 31 |
| Повторить последний вызов | 68 | 68 | 55 |
| Удалить один вызов, все позиции | 204 | 107 | 7 |
| Удалить первый найденный параметр | 68 | 28 | 12 |
| Изменить первый найденный параметр | 68 | 25 | 0 |
| Заменить создание пустого файла через touch на echo с пустой строкой | 19 | 19 | 19 |

Параметр в варианте удаления может быть необязательным: 12 успешных совпадений не обязательно являются ошибками checker. Повтор последнего вызова в 13 случаях заканчивается ошибкой, хотя конечное состояние не меняется; требование «все вызовы успешны» — отдельный выбор метрики, его нельзя автоматически приравнивать к невыполнению конечной цели.

Пустой план оставляет тот же operational state в 20 случаях и content state в 28. Поэтому **чистая проверка изменений файлов засчитала бы часть задач чтения, даже если агент ничего не сделал**. Для них нужен checker полученного/переданного ответа или task-specific наблюдаемого результата.

При этом эквивалентные планы существуют. В `ClarifyBench_A/39df4ecd.json` удаление touch перед echo не меняет финальное дерево, текущий каталог и результаты чтения: echo сам создаёт файл. Для текущего известного начального состояния это допустимая реализация; нельзя переносить вывод на другие начальные состояния, где touch должен сигнализировать существующий файл. В 19 случаях замена touch на echo(empty) также воспроизводит тот же операционный результат.

## 5. Явная конечная цель допускает разные планы

Добавлен **наш собственный маленький fixture**, не новая задача официального benchmark: создать определённый файл с заданным содержимым во вложенной папке и сохранить остальные файлы. Проверяется желаемое дерево; текущий каталог не входит в эту конкретную цель.

| План | Цель выполнена |
|---|---|
| mkdir → cd → touch → echo | Да |
| mkdir → cd → echo | Да |
| Основной план + возврат в корень | Да |
| Основной план + дополнительное чтение | Да |
| Пропустить запись содержимого | Нет |
| Записать неправильное содержимое | Нет |
| Создать лишний файл | Нет |
| Изменить порядок так, что появится файл не в той папке | Нет |

Во всех четырёх отрицательных вариантах API-вызовы сами по себе могут завершиться успешно. Именно конечный predicate отличает неверный результат. Возврат в корень показывает и обратное: operational state другой, но явно заданная пользовательская цель всё равно выполнена. Это рабочая демонстрация нужного типа checker, без претензии на независимую агентную валидацию.

## 6. Проверенные особенности и ошибки реализации

На собственных минимальных входах подтверждены:

- **Копирование директории разделяет объекты файлов:** изменение файла в копии изменяет исходный. В [cp](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/plugins/gfs_plugin.py#L761) используется поверхностная копия словаря.
- **У скопированной вложенной директории сохраняется parent исходного дерева:** `cd ..` после входа в такую директорию возвращает в исходную папку.
- **diff игнорирует непарные строки в конце:** сравнение короткого файла с тем же префиксом и дополнительной строкой возвращает пустую разницу; в [diff](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/plugins/gfs_plugin.py#L624) используется zip.

Эти три примера — stress checks возможностей плагина. В literal gold replay общие файловые объекты и неправильные parent не обнаружены, поэтому не утверждаем, что эти ошибки испортили все рассмотренные задачи.

Другие важные семантические ограничения по коду: sort только возвращает отсортированный текст, не записывает его обратно; `find(path=...)` использует текущую директорию для поиска, а path — как префикс возвращаемых строк. Они требуют явного учёта при постановке цели и не должны восприниматься как полноценная семантика Unix.

## 7. Решение для нашего исследования

GFS может дать конечную наблюдаемую награду вида «создан правильный файл / сохранены остальные данные», если checker написан по независимой спецификации задачи. Но готового надёжного массового перехода `gold calls → правильный финальный результат` здесь нет. Для чтения нужен отдельный result checker. Частичные ответы и «не знаю» ещё не подключены; их значение нельзя выводить только из совпадения аргументов вызова.

Если возвращаться к GFS, ограничить новый явно авторский набор операциями file create/write/read, задать стартовый cwd и desired state/answer отдельно от эталонного плана, проверить альтернативные планы и отрицательные случаи, затем валидировать вручную. Скопированные директории и diff пока исключить либо исправлять в отдельной версионированной модификации. Это станет **нашей модификацией/подмножеством**, а не официальным ClarifyBench score.

Сейчас рациональнее проверить другую внешнюю среду с уже предусмотренным terminal-state checker, чем чинить все gold и доменные API ClarifyBench. Результат отрицательный для быстрого выбора этой среды, но полезный: он предотвращает обучение на метрике, которая не гарантирует правильное конечное решение.
