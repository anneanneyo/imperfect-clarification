# E007 — конечное состояние retail в τ³-bench

27 октября 2026. Зафиксировано до первого исполнения retail tools.

**Задача:** проверить, можно ли получить воспроизводимый компонент конечного исхода для внешнего эксперимента об уточнениях. Это проверка измерения, не оценка агента и не эксперимент H3.

Источник: [официальный v1.0.1](https://github.com/sierra-research/tau2-bench/tree/fc0055dc4e0a316c3f83133267fbd6faaa770992), commit `fc0055dc4e0a316c3f83133267fbd6faaa770992`. Это поддерживаемый исторический релиз; текущая main уже отличается. Число retail задач: 114, авторский train=74, test=40. Код и данные MIT; ничего не устанавливаем.

Проверены исходники retail models/tools и необходимые определения toolkit/DB. Собственный загрузчик извлекает только просмотренные AST definitions, не импортирует пакет с LLM/voice зависимостями. Tool methods исполняются без изменения тел. Будет использована установленная Pydantic из bundled Python 3.12. Полные registry, orchestrator, conversation, tool-output replay и LLM judges не исполняются. Это **domain component replay**, не официальный benchmark score.

## До запуска

1. Проверить commit и SHA256 исполняемых файлов и данных.
2. Для всех 114 задач воспроизвести записанные reference actions из новой копии DB, сохранить ошибки и контроль повторного воспроизведения. Не исключать неудачи из знаменателя. В данных `initial_state=null`; иные настройки должны остановить этот протокол.
3. Для 12 train-задач с хотя бы одним WRITE tool выбрать первые по SHA256(`E007-v1:` + task_id), до исполнения и без отбора по успеху. Сохранить fixture manifest.
4. Для этих задач выполнить: пустой план; только WRITE; пропустить первый WRITE; испортить идентификатор первого WRITE; добавить READ; добавить независимое незапрошенное изменение адреса; перевернуть порядок; повторить первый WRITE.
5. Сравнить полное конечное содержимое DB с reference state, отдельно записать ошибки исполнения. Дополнительный READ и пропуск ненужных READ должны быть инвариантны в DB-компоненте. Удаление изменения и дополнительная запись обычно должны менять state; исключения исследовать, не менять автоматически метку под ожидание.
6. Статическая инспекция обнаружила потенциальный reuse последнего `variant` при изменении нескольких items. Проверить соответствие **только изменённых items** каталожным price/options сразу после успешного `modify_pending_order_items`. Исторические цены остальных товаров с текущими не сравнивать.

## Ограничения и критерий решения

Эквивалентность DB сама по себе не проверяет подтверждение пользователя, высказывания, правила обслуживания и намерение. В релизе 112/114 retail задач имеют reward basis `DB + NL_ASSERTION`; у 40 задач assertions непустые. Поэтому никакую полученную здесь долю нельзя назвать task success.

Если reference actions регулярно не исполняются, не использовать весь набор без разбора ошибок. Если компонент работает, сохранить его для ограниченного пилота, затем восстановить полный reward contract и проверить вопросы/ответы. Известные дефекты данных/метаданных публиковать отдельно; наш исправленный вариант не выдавать за официальный.

Новые модели, API, обучение и человеческие данные отсутствуют. Проверка всех публичных gold не делает их закрытым независимым test для последующих исследовательских решений. Внешнее сравнение методов пока не выполнено.

## Уточнение проверки после независимого review

После первого запуска изменён только диагностический код проверки item metadata: вместо поиска первого объекта по `new_item_id` сравниваются действительно изменившиеся объекты items по идентичности и состоянию до/после вызова. Это устраняет потенциальное ложное срабатывание на ранее существовавшем дубликате с исторической ценой. Доменные tool methods, reference actions, DB-сравнение, выбор 12 задач и мутации не изменены. Независимая побъектная проверка подтвердила исходные 9 несоответствий в 5 задачах; это исправление validation, не настройка гипотезы под результат.
