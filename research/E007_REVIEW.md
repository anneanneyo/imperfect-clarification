# E007: независимая проверка загрузчика и конечного состояния

27 октября 2026. Проверены [протокол](E007_PROTOCOL.md), [код replay](../experiments/tau3_retail_state_probe.py), pinned upstream `fc0055dc4e0a316c3f83133267fbd6faaa770992` и сохранённые результаты. Review относится к offline retail domain component; официальный агент, полная reward function, LLM judge и conversation replay не запускались.

**Вывод review:** блокирующих ошибок в измерении DB-компонента после уточнения diagnostic metadata check не обнаружено. Основные численные результаты воспроизводятся. Нельзя представлять их как официальный task success или считать каждый ошибочный gold-вызов дефектной задачей.

## Проверено независимо

- Все входные SHA256 и commit совпадают с зафиксированными значениями.
- AST-loader сохраняет тела RetailTools и используемые dispatch methods. Исключены package imports, startup/demo blocks и ненужные schema/prompt helpers; это обоснованный компонентный запуск, не эквивалентность всего пакета.
- Вызовы используемых методов не требуют пропущенных globals. Неиспользуемые DB.load/get_hash и другие helpers не следует вызывать из извлечённого namespace как полноценную замену пакета: их внешние импорты намеренно отсутствуют.
- Каждый replay создаёт новый RetailDB через deepcopy и Pydantic validation. После 17 независимых replay исходный raw DB не изменился. При проверке raw → model_dump ни одно исходное поле данных не потеряно.
- Сравнение сериализует весь типизированный DB с отсортированными ключами. Это проверка равенства состояния, а не равенства списка действий. Сам SHA256 по форматированию отличается от upstream get_dict_hash; в отчёте и не утверждается равенство официальных строк хешей. Отношение равенства содержимого здесь то же.
- Все 12 выбранных train fixtures повторены с одними mutating actions: во всех получено то же DB, что при полном reference replay.
- Дополнительный незапрошенный адрес относится к пользователю, не затронутому reference actions ни одной из 12 задач. Поэтому это действительно отдельная отрицательная проверка лишней мутации.
- Фикстуры выбраны по хешу task ID до исполнения, а не по успеху. В наборе есть задача 46 с ожидаемыми ошибочными READ-вызовами: её не исключили ради улучшения статистики.

## Ошибки gold-вызовов: необходимая интерпретация

99/114 последовательностей не имеют исключений; **15 с исключениями не равны 15 неуспешным задачам**.

| Задачи | Что проверено |
|---|---|
| 46, 47 | Сценарий прямо требует сначала сообщить неверный order ID, затем исправлять его после уточнения. Ошибки поиска ожидаемы. |
| 67, 68 | Сценарий прямо задаёт неверный ZIP с последующим исправлением. Это часть задачи. |
| 35, 54, 55 | У пользователя несколько идентификаторов/email; первая попытка поиска не находит пользователя. Не основание автоматически исключать задачу. |
| 2, 3, 4 | Reference get_product_details обращается к ID, отсутствующему в этой версии и среди product ID, и среди variant ID. Причину расхождения нужно рассматривать отдельно. |
| 37, 38, 39 | Ошибки поиска пользователя по исходным данным; без отдельной проверки intention не классифицируются как дефект benchmark. |
| 64 | Ошибочный exchange сопровождается последующим успешным modify_pending. Это fallback, а не автоматическое доказательство невозможности задачи. |
| 105 | Единственный reference exchange отклоняется из-за недостаточного gift-card balance, тогда как NL assertion требует обменять оба товара. Это локальная несогласованность reference/состояния/assertion; не утверждение о всём benchmark. |

В evaluator_env.py upstream исключения во время применения golden actions тоже логируются, после чего обработка продолжается. Поэтому выбранное в E007 продолжение после ошибки соответствует этому аспекту построения gold DB. Но E007 не воспроизводит проверку записанных tool outputs при set_state, а ошибочные READ не означают неправильный конечный DB.

## Независимая проверка ошибки item metadata

Исходная диагностика искала первый item с соответствующим new_item_id. При наличии ранее существовавшего такого же variant она могла бы проверить неизменённый товар с исторической ценой. С разрешения автора E007 этот участок уточнён: сохраняются объекты и их значения до вызова, после проверяются только действительно изменившиеся объекты. Протокол дополнен пометкой **validation repair**; тела upstream tools, гипотезы, фикстуры и сравнение DB не изменены.

Повторная проверка по идентичности объектов независимо подтвердила:

| task_id | Неправильных изменённых items |
|---|---:|
| 20 | 3 |
| 21 | 1 |
| 36 | 2 |
| 37 | 2 |
| 100 | 1 |
| Всего | **9 в 5 задачах** |

Во всех девяти случаях записанные price/options соответствуют **последнему** запрошенному variant, а не variant конкретного item. Это согласуется с исходником: variable `variant` вычисляется в первом цикле, а затем переиспользуется во втором без обновления. Исторические цены неизменённых товаров не использованы как основание претензии. Reference state детерминирован, но такое совпадение DB само по себе не гарантирует семантически правильные данные заказа.

После diagnostic repair повторён полный E007: 114 reference replay × 2 и 96 мутаций; показатели 99/114 без исключений, 103 изменённых DB и 9 metadata mismatches в пяти задачах сохранились.

## Что результаты мутаций не доказывают

WRITE-only и extra READ совпадают с gold DB, потому что считывания не меняют этот компонент. Это не проверка информирования пользователя, его согласия или соблюдения условий обслуживания. Обратный порядок случайно сохранил DB во всех 12 выбранных fixtures; это не общий закон перестановочности. Повтор WRITE сохранил DB в 12 случаях, но в 10 породил ошибку: DB-эквивалентность и качество диалога различаются.

В данных 112/114 задач включают DB+NL_ASSERTION в reward basis, а у 40 есть непустые NL assertions. Полные policy/диалоговые требования и конечные ответы пока не измерены. Все публичные reference actions уже просмотрены, поэтому выбор этих же задач для новых решений нельзя называть нетронутым независимым test.

Численная проверка сохранена в [review.json](../results/tau3_retail_state_probe/review.json): проверенные ID, результаты независимого WRITE-only replay, подтверждение девяти mismatches, контроль сохранности raw DB, хеш проверенного скрипта. Исходный checkout не изменялся.
