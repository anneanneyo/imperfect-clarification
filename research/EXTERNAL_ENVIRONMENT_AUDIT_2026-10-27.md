# Внешняя среда: аудит воспроизводимости, 27 октября 2026

**Решение:** следующим кандидатом для небольшой проверки оставить **ClarifyBench**, но пока не объявлять внешнюю среду готовой. Данные доступны, однако опубликованный код требует проверки evaluator, а авторский SAGE-Agent в зафиксированном релизе не найден. **Clarification-enhanced τ-bench из IG-clarifier сейчас нельзя воспроизвести из его публичного релиза:** опубликован тренер, но не экспериментальные данные и evaluation harness.

Это продвижение пункта 6 [плана руководителя](/Users/annagubareva/Downloads/PLAN.md): выбор по доступности данных, воспроизводимости, лицензии и проверке конечного результата. Это **не** завершённое сравнение H3 и **не** выполненная внешняя агентная оценка.

Собственный скрипт читает JSON и Python AST, считает состав и пересечения данных и сохраняет SHA-256 файлов. **Чужой код не импортировался и не запускался; пакеты и модели не устанавливались; вызовов моделей — 0.**

## Сравнение кандидатов

| Критерий | ClarifyBench / SAGE-Agent | IG-clarifier / clarification-enhanced τ-bench |
|---|---|---|

| Реальные доступные данные | 213 ambiguous, 241 explicit, 148 infeasible, всего 602 непустых задания | Train/eval данные отсутствуют; README прямо называет релиз code-only |
| Разбиение | A/E/I — типы запросов, **не train/validation/test**. Есть общие сценарии между типами | Статья сообщает 500 retail train trajectories, 115 retail test, 50 airline test; воспроизводимые обработанные splits не приложены |
| Авторский метод | В `config.py` зарегистрирован только `baseline`; соответствующий класс явно описан как упрощённый ReAct. Полного SAGE/EVPI selection loop не найдено | IG training loop есть; checkpoint обученного clarifier и pipeline paper-evaluation не найдены |

## Что обнаружено в ClarifyBench

### 1. Число доступных заданий отличается от общего числа на странице работы

[Страница автора](https://manansuri.com/papers/sage-clarification/) указывает 716 задач. В проверенном дереве — **602 непустых JSON-сценария** в A/E/I. Это наблюдение о доступном релизе, а не объяснение причин расхождения.

| Домен | Ambiguous A | Explicit E | Infeasible I |
|---|---:|---:|---:|
| Документы | 49 | 49 | 36 |
| Управление автомобилем | 39 | 50 | 35 |
| Торговля акциями | 46 | 49 | 29 |
| Поездки | 40 | 50 | 14 |
| Файловая система | 39 | 43 | 34 |
| **Всего** | **213** | **241** | **148** |

Помимо них лежат пустые объекты `ClarifyBench_A/1aebdf65.json` и `ClarifyBench_E/7f84ca77.json`. Все десять файлов `sample/` совпадают с файлами основных подмножеств по содержимому. Их нельзя добавлять к объёму данных или считать независимым тестом. Подсчёты, идентификаторы и хеши находятся в manifest.

### 2. Одинаковые сценарии встречаются под разными идентификаторами

Посчитан хеш тройки **API + начальная конфигурация + gold tool calls**, без текста запроса. Найдено 178 общих хешей между A/E, 74 между A/I и 84 между E/I. Это количество общих уникальных хешей, не число независимых людей или эпизодов.

**Следствие для нашего исследования:** нельзя обучаться на E и тестироваться на A, объявляя это независимым переносом. Разбивать надо группами исходного сценария, удерживая все его варианты в одной части. Точное совпадение хеша — только нижняя граница зависимости; близкие шаблоны нужно проверять дополнительно.

### 3. Штатная метрика не равна проверке итогового состояния

В [evaluator](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/simulation/evaluation.py#L880) итоговый `success` складывается из совпадения final calls с gold и отсутствия неуспешных выполнений. State-based evaluation явно пропущена. `coverage` проверяет присутствие эталонных вызовов; оно само по себе не штрафует лишние действия.

Кроме того, [exact-match функция](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/simulation/evaluation.py#L483) для каждого gold-вызова берёт **первое** совпадение по имени инструмента. Если инструмент вызывается дважды с различными аргументами, даже правильный список вызовов может не пройти эту функцию: для второго gold-вызова снова берётся первый actual-вызов. Такие разные аргументы у повторного инструмента есть в 29 заданиях A, 32 E и 12 I. Это вывод из чтения функции и анализа данных; оригинальный evaluator в этом блоке не исполнялся, score модели не вычислялся.

[Скрипт агрегации](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/evaluate.py#L214) также пропускает файлы с `error`. Для нашего протокола нужен полный список запланированных эпизодов: долю технических ошибок показывать отдельно, знаменатель не уменьшать молча.

### 4. Пользователь — ещё одна модель, а не бесплатная функция из готовых ответов

[UserSimulator](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/llm/simulation.py) видит скрытую цель и генерирует ответ на вопрос с лимитом 500 output tokens. Агент и симулятор получают один provider в [main.py](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/main.py#L178). Поэтому бюджет включает обе стороны диалога. По конфигурации установлено до пяти уточнений на запрос; точный денежный бюджет без выбранной модели и реальных длин запросов пока не измерен.

В 212 из 213 заданий A хотя бы у одного gold-вызова нет `turn`; загрузчик присваивает отсутствующим `turn=1`. При будущей multi-turn проверке отдельно проверить, не раскрывает ли симулятор будущие намерения: одного текста инструкции «не раскрывать» для доказательства изоляции недостаточно.

## Что можно и нельзя взять из исходного τ-bench

Проверен **исходный τ-bench как диагностическая альтернатива**, а не как уже восстановленная версия IG. У него есть [MIT LICENSE](https://github.com/sierra-research/tau-bench/blob/59a200c6d575d595120f1cb70fea53cef0632f6b/LICENSE), retail train/dev/test = 500/20/115 и airline test = 50. В [base.py](https://github.com/sierra-research/tau-bench/blob/59a200c6d575d595120f1cb70fea53cef0632f6b/tau_bench/envs/base.py#L121) reward сопоставляет хеш базы после действий агента с базой после gold-действий, дополнительно проверяя требуемые текстовые outputs. Это ближе к требуемому конечному execution checker, чем совпадение вызовов. Проверка не гарантирует соблюдение всех промежуточных правил.

Однако [текущий README](https://github.com/sierra-research/tau-bench/blob/59a200c6d575d595120f1cb70fea53cef0632f6b/README.md) предупреждает об устаревших задачах и направляет к τ³-bench. Нельзя взять старую среду, придумать собственную обфускацию запросов и назвать полученное воспроизведением IG-clarifier. Новую модификацию придётся явно описать и сравнивать отдельно. τ³ в этом блоке не аудирован; новые домены сейчас в обязательный объём проекта не добавляем.

Ресурсы IG для полного обучения существенно больше простого evaluation: авторы указывают четыре RTX A6000 и 7–12 часов на запуск; эти цифры — их конфигурация, не измерение на нашем компьютере. Не начинать с репликации RL ради получения первого внешнего результата.

## Конкретная следующая проверка без модели и оплаты

**Следующий минимальный результат — аудит correctness evaluator на эталонных и испорченных траекториях ClarifyBench.** Это проверка измерительного инструмента до измерения методов.

1. Закрепить 12 публичных сценариев из A/E: разные домены, в том числе не менее трёх с повторным использованием одного инструмента. Их статус — development fixtures, не финальный test.
2. После отдельного просмотра зависимостей evaluator подать эталонную последовательность вызовов и контролируемые повреждения: неверное значение аргумента, пропуск, лишнее действие, перестановка зависимых действий, два вызова одного инструмента с разными аргументами. Исходники и исправления вести отдельно.
3. Записать ожидаемую и фактическую реакцию штатной метрики. Исправленный checker обозначить как нашу версию; никогда не подменять им официальный score без пояснения. Для state-based success разработать и проверить конечные состояния хотя бы одного домена; если это существенно разрастается, предпочесть среду с готовым checker.
4. Сформировать groups по сценариям и зафиксировать development/test до обучения. Для изучения H3 оставить одинаковые вопросы, executor и бюджет для прямого и факторизованного оценивателей.
5. Только после прохождения этих проверок планировать маленький запуск ReAct и utility-aware controls. Не обозначать собственную реализацию по статье как «авторский SAGE». Неполные/IDK ответы добавлять как **отдельную авторскую модификацию**; сначала воспроизвести исходный режим.

Для принятия окончательного решения по среде нужны: разрешённый путь публикации материалов, корректный конечный checker и доступный сильный baseline. Сегодня подтверждён только доступ к материалам ClarifyBench, а не все три условия. Этот аудит устраняет риск потратить большой запуск на среду, метрики и разбиение которой ещё не проверены.

## Воспроизводимость аудита

Команда использует только собственный анализатор и стандартную библиотеку Python:

```bash
python3 results/external_environment_audit/audit_static.py \
  --clarify /private/tmp/clarifybench-audit-20261027 \
  --ig /private/tmp/ig-clarifier-audit-20261027 \
  --tau /private/tmp/tau-bench-audit-20261027 \
  --output results/external_environment_audit/manifest.json
```

Временные каталоги не являются постоянным хранилищем. Для повтора следует скачать перечисленные публичные репозитории, выбрать закреплённые commits и передать их новые пути. Скрипт проверяет commits и отказывается молча анализировать новую версию. В manifest сохранён полный хешированный список файлов; он не содержит содержимого чужих данных или секретов.
