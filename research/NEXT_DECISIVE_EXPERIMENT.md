# Следующий этап: проверяемая семантика решений после E025

8 ноября 2026. [Результат E025](REPORT_2026-11-08_E025.md), [протокол E025](E025_PROTOCOL.md), [контракт E024](USERBENCH_SOURCE_GATE.md), [E023](E023_RESULTS.md).

Тема сохраняется. Банковский источник остаётся диагностикой; E021 не запущен, резерв E023 не оценён. E025 завершил первый train-аудит UserBench и выявил проблему метрики: source-best не всегда соответствует конкретному тексту предпочтения, цена часто задана только категорией. Официальный test не использовать для настройки.

1. Новый протокол E026 до подсчёта новых исходов. Использовать те же 12 development-задач, без замены неудобных примеров. Для 96 предпочтений описать критерий по видимым полям вариантов: проверяемый, неоднозначный или не проверяемый по данным. Не трактовать отсутствие свидетельства как автоматическое нарушение.
2. Сохранить source-метки рядом с нашей интерпретацией. Ресторанные tie-множества и два контрпримера должны оставаться в отчёте. Для новых семантических метрик нужна независимая проверка; один ассистент не считается вторым независимым разметчиком.
3. Отделить минимальный набор удовлетворённых потребностей от оптимизации цены. Задать обработку необязательных услуг, относительных пожеланий и ценовых категорий; не выдумывать числовые цены или недостающие свойства. Если критерия нет — результат unknown, а не удобная метка.
4. Заранее определить публичное меню вопросов. Не формировать его только из активных скрытых предпочтений задачи: это подсказало бы агенту, о чём нужно спрашивать. Публичный вход и исполнитель одинаковы для всех методов.
5. Определить распределение скрытых целей и ответов, необходимое для ожидаемой пользы. В исходной задаче есть один конкретный профиль; сам по себе он не задаёт контрфактическое распределение. Любые наши профили/partial/unknown-каналы обозначить как синтетическую модификацию. Не повторять сценарий с выигрышем, почти полностью объясняемым постоянными частотами ответов.
6. Перед обучением проверить, бывают ли хотя бы на диагностических задачах разные оптимальные вопросы, и отделить oracle от реализуемого выбора. После этого закрепить бюджеты, разбиение с контролем шаблонов, no-ask/constant/heuristic/direct/factorized сравнения. Граф всех 96 train-задач связен: простое деление целых задач с сохранением всех строк не даёт непересекающихся шаблонов.

Готовый оценщик E025 уже отделяет окончательный выбор от промежуточных наград; менять его замороженную версию не нужно. Новая семантическая версия — отдельным файлом. E026 ещё не запущен. Ближайший результат должен показать, какие решения можно оценивать содержательно и существует ли здесь проверяемая задача выбора вопросов, прежде чем тратить ресурсы на обучение.
