# E006: штатный checker ClarifyBench проверен исполнением

27 октября 2026. По [зафиксированному протоколу](E006_PROTOCOL.md). **Найдена и воспроизведена ошибка сопоставления повторных вызовов в публичном evaluator.** В 73 сценариях точная копия непустой эталонной последовательности не признаётся exact match. В двух других сценариях пропуск повторного вызова, замещённого лишним действием, ошибочно признаётся exact match и общим success.

Это проверка измерительного кода на искусственных логах вызовов. **Ни одна LLM policy и ни один инструмент ClarifyBench не запускались.** Результат не опровергает таблицы статьи: не установлено, что её эксперименты вычислялись именно этим релизом и этим путём оценки.

## Что и как исполнено

Источник — [ClarifyBench commit a85d4f9](https://github.com/MananSuri27/ClarifyBench/tree/a85d4f9df1fc87d05c713fd408f8a57d72bcc348). Просмотрен `simulation/evaluation.py`; через AST извлечены восемь нужных методов без изменения тел. Импорт проекта, агента, симулятора и plugins исключён. Проверяются полный SHA-256 evaluator и разрешённые встроенные вызовы. Нужны только стандартные библиотеки Python.

Переданы 602 непустых JSON-сценария A/E/I. В одном из них список gold-вызовов пуст; ещё два исходных JSON являются пустыми объектами и отдельно перечислены в summary. Десять sample-дубликатов не добавлены. Флаги `was_executed=True, success=True` в построенных логах искусственные: они позволяют изолировать matching, но не доказывают исполнимость действий. Для infeasible-подмножества это особенно существенно.

Для отдельного просмотра детерминированно выбраны 12 fixtures, охватывающие все пять доменов; три содержат повторные инструменты. Их пути сохранены в summary. В итоговых counts используются **все** 602 сценария, а не отобранные fixtures.

## 1. Проверка эталона самим собой

Ожидание этой проверки узкое: если actual calls точно повторяют gold calls, синтаксический exact match должен срабатывать. Это не утверждение об успешном выполнении gold в реальной среде.

| Подмножество | Записи | Exact match=True | Полное coverage=True | Отказ exact на непустом идентичном gold |
|---|---:|---:|---:|---:|
| Ambiguous | 213 | 183 | 212 | 29 |
| Explicit | 241 | 209 | 241 | 32 |
| Infeasible | 148 | 136 | 148 | 12 |
| **Всего** | **602** | **528** | **601** | **73** |

Причина подтверждена на всех 73 случаях: у одного имени инструмента есть несколько вызовов с разными параметрами. [Функция exact match](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/simulation/evaluation.py#L483) для каждого gold-вызова выбирает первый actual-вызов с тем же именем. Для второго вызова снова сравнивается первый набор параметров. Это не взаимно однозначное сопоставление.

Собственный минимальный пример: gold и actual равны `[set_value(1), set_value(2)]`. Наше строгое сравнение списков возвращает True, штатный exact match — False, param_match_rate — 0.5, coverage — 1.0. Искажение затрагивает не только общий success, но и долю совпавших параметров.

Отдельная запись `ClarifyBench_A/cdb2ba59.json` имеет пустой gold. На пустом actual evaluator возвращает early failure и не заполняет coverage/param_match_rate. Она не включена в число 73 ошибок повторного сопоставления; правильную задачно-смысловую трактовку пустой цели ещё надо установить.

## 2. Контролируемые изменения вызовов

В таблице знаменатель — число применимых сценариев данного изменения. У каждого изменения есть собственное назначение; например, coverage по определению полноты может сохраняться при лишнем действии. Его нечувствительность к лишним действиям **сама по себе не является багом**, но запрещает трактовать coverage как доказательство правильного конечного результата.

| Изменение | Выполнено | Exact=True | Coverage=True | Общий success=True |
|---|---:|---:|---:|---:|
| Удалить первый вызов | 601 | 0 | 8 | 0 |
| Добавить дубликат первого | 601 | 0 | 601 | 0 |
| Добавить лишнее действие своего домена | 601 | 0 | 601 | 0 |
| Изменить значение одного параметра | 594 | 0 | 0 | 0 |
| Обратить порядок, если последовательность меняется | 558 | 485 | 558 | 485 |
| Добавить неуспешную попытку перед правильным финалом | 602 | 528 | 602 | 0 |
| Удалить один полностью идентичный повтор | 9 | 0 | 9 | 0 |
| Заменить такой повтор лишним действием, сохранив длину | 9 | **2** | **9** | **2** |

Последняя строка — уже **ложное принятие по точному совпадению**, а не просто ограничение recall/coverage. В `ClarifyBench_I/cf349775.json` и `ClarifyBench_I/f0debcf4.json` один повторный вызов заменён `fillFuelTank` из другого опубликованного сценария. Strict multiset equality=False, а штатные exact_match и success=True. Мы не выполняли заправку и не проверяли её корректность в данном состоянии; доказано несовпадение call lists.

Механизм: проверка длины списка проходит, а один actual-вызов повторно используется как подтверждение нескольких одинаковых gold-вызовов. Лишний actual-вызов не обязан ни с чем сопоставиться. Из девяти таких мутаций другие семь не проходят, поскольку их исходные gold уже страдают противоположной ошибкой с разными параметрами повторного инструмента.

Собственный контроль показывает возможное следствие для состояния: gold `[set_value(1), set_value(1)]`, actual `[set_value(1), delete_value()]`. Штатный success=True, но наша простая переменная в конце actual отсутствует, тогда как в gold равна 1. Это **искусственный иллюстративный пример**, не measured outcome задачи ClarifyBench.

## 3. Порядок и восстановление после ошибок требуют отдельного определения успеха

485 обращённых последовательностей получают exact match и success=True. Это не означает 485 ошибочно выполненных задач: часть действий может быть независимой. Вывод уже: метрика не проверяет порядок. На нашем примере разных инструментов `set_value(1) → add_value(2)` и обратного порядка checker принимает обе последовательности, хотя итоговые значения 3 и 1 различаются.

Если добавить одну неуспешную попытку перед правильными final calls, execution_success становится False во всех 602 случаях. Это заложенное [определение общего success](https://github.com/MananSuri27/ClarifyBench/blob/a85d4f9df1fc87d05c713fd408f8a57d72bcc348/simulation/evaluation.py#L880), не установленная ошибка реализации. Однако это метрика безошибочности всех попыток, а не только качества конечного состояния после восстановления. Для нашего исследования нужно заранее выбрать, что именно является конечной потерей.

## 4. Ограничения вывода

- Все логи сконструированы; натуральные ошибки моделей и частота этих ситуаций в их поведении не измерялись.
- Не сравнивались SAGE, IG или наш оцениватель вопросов. Нет нового результата о качестве уточнений и нет проверки H3.
- 602 записи связаны между собой вариантами сценариев. Статистические интервалы по ним как по независимым задачам не вычислялись.
- Строгие ordered/multiset comparisons — только диагностические ориентиры. Они не признают автоматически семантически эквивалентные планы и не заменяют state-based checker.
- Нельзя вывести из этого аудита, насколько изменится рейтинг методов статьи. Для этого потребуются реальные траектории соответствующей версии и пересчёт.
- Исправление checker не добавлено в официальный репозиторий; авторам ничего не отправлено. Отсутствие найденной лицензии и неполнота релиза SAGE остаются отдельными вопросами из [аудита доступности](EXTERNAL_ENVIRONMENT_AUDIT_2026-10-27.md).

## Решение для проекта

**Не использовать текущий `success` как единственный надёжный конечный outcome для обучения или проверки нашей модели.** Иначе оцениватель пользы вопроса начнёт обучаться, в том числе, на ошибках matcher.

Ближайший технический шаг — независимый one-to-one call matcher с явно заданной обработкой повторов, числовых типов и порядка; его версию и score показывать отдельно от upstream. После этого нужен проверенный checker конечного состояния хотя бы одного домена либо другой опубликованный benchmark с готовым checker. Простое исправление первой найденной ошибки ещё не выполняет этот второй шаг.

Публикационный вывод остаётся ограниченным: найден воспроизводимый дефект публичного измерительного инструмента и исключён ненадёжный путь оценки нашей основной гипотезы. Одного такого аудита недостаточно для обещанной статьи о выборе уточняющих вопросов.
